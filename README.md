# Managed Keycloak deployment template

A starting point for the Git repository that deploys a
[VSHN Managed Keycloak](https://docs.appcat.ch/vshn-managed/keycloak/) (AppCat) on
with Helm through GitHub Actions.

## About this template

Maintained by the [Keycloak Competence Center](https://keycloak.ch), third level
support for VSHN Managed Keycloak. Create your own repository from it with **Use
this template**, fill in the placeholders and replace the example realm. See
[CHANGELOG.md](CHANGELOG.md) for what changed.

Not covered: custom Keycloak images and DNS.

## Layout

```text
helm/                     Helm chart for the Keycloak deployment
  templates/              Kubernetes manifests rendered by Helm
  values.yaml             shared defaults
  values.test.yaml        test environment overrides
  values.prod.yaml        production environment overrides
examples/                 optional examples
  vault/                  the Secret from the Vault Secrets Operator instead
.github/
  actions/                shared GitHub Actions
  workflows/              validation and deployment workflows
docker/                   optional custom image support
```

The deployment is rendered from the Helm chart and deployed by GitHub Actions.
Environment-specific values live in `helm/values.test.yaml` and
`helm/values.prod.yaml`.

## Prerequisites

* A namespace with the AppCat Keycloak offering enabled, see [AppCat Product](https://products.vshn.ch/appcat/index.html).
* A Kubernetes config for each target cluster or namespace, provided to GitHub
  Actions as repository secrets.
* A DNS CNAME for the FQDN pointing at your APPUiO zone endpoint, for example
  `cname.cloudscale-lpg-0.appuio.cloud`. The certificate is then issued and renewed
  for you.
* The mandatory GitHub Actions repository secrets and variables described below.

## GitHub Actions configuration

The deployment workflows require the following **repository secrets**:

* `APPFLOW_MONITORING_EMAIL`
* `APPFLOW_EXAMPLE_CLIENT_SECRET`
* `KUBECONFIG_TEST`
* `KUBECONFIG_PROD`

For real deployments, consider using separate GitHub environments for test and
production. This lets you scope environment-specific values separately, especially:

* `APPFLOW_EXAMPLE_CLIENT_SECRET` for test and production
* `KUBECONFIG_TEST`
* `KUBECONFIG_PROD`

## Setup

1. Adjust `helm/values.yaml`, `helm/values.test.yaml` and `helm/values.prod.yaml`
   for your instance name, hostnames, sizing, maintenance window and service level.
2. Replace the example realm with your realm export, or adapt it to your needs.
3. Configure the mandatory GitHub Actions repository secrets and variables, see [Github Actions configuration](#github-actions-configuration).
4. Push your changes and let the GitHub Actions workflows validate and deploy the
   Helm release.

## Realm configuration

`service.customConfigurationRef` names a ConfigMap in the claim namespace. Every key
in it becomes a file under `/opt/keycloak/setup/project`, and [keycloak-config-cli](https://github.com/adorsys/keycloak-config-cli)
imports all of them on every start. The ConfigMap is generated by Helm from the
realm JSON files in the chart.

Realm JSONs can reference environment variables as `$(env:NAME:-default)`. The
values come from whatever `service.envFrom` points at, which is how the same realm
export serves several environments: secrets and per-environment hostnames stay out
of the JSON. A common pattern is `"enabled": "$(env:SOME_CLIENT_ENABLED:-false)"`,
so a client exists in every environment but is only switched on where it is wanted.

Imports are additive. Removing a client from the JSON does not remove it from
Keycloak.

## Environment variables

`service.envFrom` reads two objects, and the split decides what ends up in Git:

* the environment ConfigMap, committed here, holds `KC_*` settings and every
  non-secret value the realm JSONs interpolate: hostnames, IdP endpoint URLs,
  timeouts and feature switches.
* the environment Secret holds client secrets and credentials, and is never
  committed.

The Secret is listed second, so it can override a key from the ConfigMap. VSHN sets
`KC_HOSTNAME`, `KC_HOSTNAME_ADMIN`, `KC_HTTP_RELATIVE_PATH`, the database settings
and the HTTPS certificate paths as container env, which outranks both.

## Environment promotion

Test and production are configured through separate Helm values files and separate
deployment workflows. Changes should be deployed to test first and promoted to
production only after review.

## Custom themes and extensions

VSHN runs its own Keycloak image. To ship custom themes or providers, build an image
from https://github.com/vshn/custom-keycloak-image-template and set
`service.customizationImage`.
